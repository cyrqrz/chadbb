# chadbb · G2.1 · Component Shape & Action Hierarchy

## Objetivo

Refinar a foundation visual do G2 sem antecipar o redesign de layout previsto para G3/G4.

O principal problema visual atual é o excesso de elementos com formato **pill/cápsula** e muitas ações delimitadas por borda. Isso cria a sensação de “retângulos dentro de retângulos”, reduz a hierarquia visual e deixa cards como os de convidados com aparência menos profissional.

A proposta deste ajuste é evoluir o **shape system**, a **hierarquia de ações**, a **arquitetura CSS** e a **acessibilidade** de forma sistêmica.

---

## 1. Regra principal de forma

> **Pills são exceção, não padrão.**

Usar `rounded-full` apenas quando a forma tiver função clara, como badges, avatars e controles realmente circulares.

### Escala sugerida

| Elemento | Radius sugerido | Uso |
|---|---:|---|
| Badge / status | `9999px` | Individual, Família · até 4 pessoas |
| Botão | `10px` | Editar, salvar, confirmar |
| Input / select | `10–12px` | Formulários |
| Card | `14–16px` | Convites, convidados, itens |
| Modal / painel grande | `16–20px` | Superfícies maiores |
| `rounded-full` | restrito | Badge, avatar, ícone circular |

Esses valores devem virar **tokens semânticos**, não números repetidos diretamente pelos componentes.

Exemplo:

```css
:root {
  --radius-control: 0.625rem;
  --radius-field: 0.75rem;
  --radius-surface: 1rem;
  --radius-panel: 1.25rem;
  --radius-pill: 9999px;
}
```

## 2. Card de convidado

O card atual deve manter sua estrutura no G2, mas perder peso visual.

### Problemas atuais

- card muito arredondado;
- botão “Editar convite de Convidado fictício X” grande demais;
- quebra de texto desnecessária;
- botão secundário também em formato pill;
- “Revogar acesso” parece link, embora seja uma ação;
- praticamente toda ação compete visualmente com as demais.

### Direção

Visualmente, usar apenas:

**Editar convite**

O nome do convidado já está no contexto do card e não precisa ser repetido dentro do botão.

Para acessibilidade, o nome completo pode permanecer disponível ao leitor de tela:

```tsx
<button>
  Editar convite
  <span className="sr-only"> de Convidado fictício 3</span>
</button>
```

Manter altura de aproximadamente `44–48px`, mas usar radius de botão normal, não pill.

---

## 3. Hierarquia de ações

Definir variantes claras e reutilizáveis.

### Button

Sugestão de API:

```tsx
<Button variant="primary" />
<Button variant="secondary" />
<Button variant="ghost" />
<Button variant="danger" />
<Button variant="icon" />
```

### Prioridade

- **Primary:** principal ação daquele contexto.
- **Secondary:** ação importante, mas não dominante.
- **Ghost / tertiary:** ações auxiliares.
- **Danger:** ação destrutiva.
- **Icon:** ações compactas com nome acessível.

Evitar várias ações com a mesma borda e o mesmo peso visual.

---

## 4. “Revogar acesso” deve ser um botão

“Revogar acesso” executa uma ação. Não é navegação.

Portanto:

- não usar elemento `<a>`;
- não depender de underline para comunicar interatividade;
- usar `<button>`;
- usar variante `danger` ou `danger-ghost`;
- garantir foco visível;
- garantir nome acessível;
- manter confirmação quando a ação for destrutiva e difícil de reverter.

No G4, pode ser avaliado mover ações destrutivas menos frequentes para um menu de ações (`…`), desde que o menu siga corretamente teclado, foco e ARIA.

---

## 5. Tokens semânticos

Evitar decisões locais como:

```txt
rounded-xl
border-pink-200
px-4
py-3
```

espalhadas pelo projeto.

Criar tokens por intenção:

```css
--color-surface;
--color-surface-subtle;
--color-border;
--color-border-subtle;
--color-text;
--color-text-muted;
--color-danger;
--color-focus;

--radius-control;
--radius-field;
--radius-surface;
--radius-panel;
--radius-pill;

--control-height-sm;
--control-height-md;

--space-control-x;
--space-card;
```

O objetivo é permitir alterações globais sem refatorar dezenas de componentes.

## 6. Componentes-base a auditar no G2.1

Prioridade:

1. `Button`
2. `IconButton`
3. `Card`
4. `Badge`
5. `Input`
6. `Select`
7. `Textarea`
8. `ActionMenu`
9. `Dialog`
10. `Pagination`

Cada componente deve definir:

- anatomia;
- variantes;
- tamanhos;
- estados;
- tokens;
- comportamento responsivo;
- contrato de acessibilidade.

---

## 7. CSS de nível de sistema

Organizar a cascade explicitamente.

Sugestão:

```css
@layer reset, tokens, base, components, utilities, overrides;
```

Evitar resolver conflitos aumentando especificidade.

Preferir:

- cascade layers;
- custom properties;
- herança;
- composição;
- progressive enhancement;
- componentes pequenos e previsíveis.

A foundation deve controlar o visual; telas não devem reconstruir o design system localmente.

---

## 8. Container Queries

Usar `@container` quando o comportamento depender do espaço disponível para o componente, e não apenas do viewport.

Exemplo de caso:

`GuestCard` pode aparecer:

- no painel mobile;
- em coluna maior no desktop;
- dentro de modal;
- futuramente em layouts diferentes.

O componente deve conseguir se adaptar à largura recebida sem depender exclusivamente de breakpoints globais.

---

## 9. Acessibilidade obrigatória

Acessibilidade não deve ser uma etapa posterior.

### Controles

- alvo de toque preferencial: `44–48px`;
- foco visível;
- semântica HTML correta;
- nome acessível;
- estado disabled perceptível sem depender só de cor;
- erros ligados ao campo;
- instruções ligadas ao controle quando necessárias.

### Contraste

Validar:

- texto normal;
- texto secundário;
- bordas necessárias para identificar controles;
- foco;
- ícones;
- estados disabled;
- danger;
- badges.

### Estados mínimos

Cada componente interativo deve considerar:

```txt
default
hover
active
focus-visible
disabled
loading/pending
error
selected
```

Também verificar:

```txt
prefers-reduced-motion
prefers-contrast
forced-colors
```

---

## 10. Movimento

Não adicionar animações apenas para “dar vida”.

Regras:

- nada essencial deve depender de animação;
- evitar animações em loop decorativas;
- respeitar `prefers-reduced-motion`;
- usar transições curtas para feedback de estado;
- animação deve explicar mudança, hierarquia ou continuidade.

A estrela da capa padrão continua sem loop.

---

## 11. Primitives acessíveis

Para componentes comportamentalmente complexos, evitar implementar manualmente toda a camada de acessibilidade.

Avaliar:

### Radix Primitives

Boa opção para:

- dialog;
- dropdown menu;
- popover;
- tooltip;
- select;
- tabs;
- focus management.

### React Aria

Boa opção quando for necessário maior controle comportamental e composição acessível.

A identidade visual continua sendo do chadbb. Essas bibliotecas devem resolver principalmente comportamento, teclado, foco e ARIA.

---

## 12. Automação de acessibilidade

Adicionar verificações em desenvolvimento e CI.

Avaliar:

- `eslint-plugin-jsx-a11y`;
- `axe-core`;
- testes com `jest-axe` ou equivalente;
- Storybook Accessibility addon, caso Storybook seja adotado;
- testes manuais por teclado;
- inspeção com leitor de tela nas jornadas críticas.

Automação não substitui teste manual.

## 14. Limite de escopo

Este ajuste pertence ao **G2/Foundation**.

Não antecipar:

- hero editorial do convite;
- mudança estrutural do painel;
- nova arquitetura de informação;
- redesign completo dos cards;
- alterações previstas formalmente para G3/G4.

O objetivo é melhorar a linguagem visual e técnica da base para que G3 e G4 partam de componentes maduros.

---

## 15. Entregável sugerido: G2.1

Criar um pequeno gate intermediário:

### `G2.1 · Component Shape & Action Hierarchy`

Escopo:

- revisar o excesso de `rounded-full`;
- formalizar a escala de radius;
- criar tokens semânticos;
- revisar variantes de `Button`;
- corrigir semântica de ações;
- reduzir peso visual dos cards atuais;
- validar contraste;
- validar foco e teclado;
- revisar responsividade dos componentes;
- impedir regressões com testes.

### Primeiro alvo visual

Começar pelo card de convidado mostrado no painel.

Critérios de aceite:

- badges continuam pill;
- cards deixam de parecer cápsulas;
- botões deixam de parecer pills;
- “Editar convite” não repete visualmente o nome do convidado;
- contexto completo permanece acessível ao leitor de tela;
- “Revogar acesso” usa semântica de botão;
- apenas a ação principal domina visualmente;
- alvos de toque continuam adequados;
- estados de foco são claramente visíveis;
- nenhuma alteração estrutural de G3/G4 é antecipada.

---

## Princípio final

A meta não é “tirar bordas” ou “diminuir radius” isoladamente.

A meta é construir uma **gramática visual consistente**:

- superfície é superfície;
- badge é badge;
- botão é botão;
- ação destrutiva parece destrutiva;
- ação secundária não compete com a principal;
- componentes compartilham tokens;
- acessibilidade faz parte do contrato do componente.

Isso deve deixar o G2 mais profissional agora e, principalmente, criar uma foundation sólida para escalar o visual no G3 e G4.
